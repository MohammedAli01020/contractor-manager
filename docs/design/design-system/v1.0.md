# Contractor Manager — Design System v1.0

**Status:** Initial baseline; shared tokens approved as a direction, individual screens remain subject to review.  
**Primary surface:** Flutter mobile app for contractors and supervisors.  
**Separate surface:** Platform Owner Web.

## 1. Product principles

- **Mobile first:** core daily workflows must be comfortable on a contractor's phone.
- **Arabic first:** Arabic labels and right-to-left layout are the default.
- **Operational clarity:** shifts, equipment, drivers, advances, expenses, inventory, treasury/banks, and reports remain understandable as distinct areas.
- **Accounting integrity:** the UI must not imply that an estimate is a posted transaction. Financial totals must follow backend rules.
- **Consistency:** shared colors, typography, spacing, components, and states are reused across screens.
- **Honest states:** loading, empty, validation, permission, offline, and server-error states are designed explicitly.

## 2. Color tokens

| Token | Value | Usage |
|---|---|---|
| Primary navy | `#153B65` | App bar, primary actions, selected navigation |
| Light blue | `#EAF2FC` | Informational surfaces |
| White | `#FFFFFF` | Main surfaces |
| Success | `#28764B` | Confirmed success / positive status |
| Warning | `#A56519` | Attention required |
| Error | `#B93838` | Failed / destructive status |
| Primary text | `#172B3A` | Main text |
| Secondary text | `#64748B` | Supporting text |
| Border | `#DCE3EA` | Dividers and outlines |
| Page background | `#F5F7FA` | App background |

Color must never be the only status indicator; pair it with text and/or an icon.

## 3. Typography

- Preferred Arabic typeface: **Cairo**, subject to Flutter rendering and licensing validation.
- Fallback: **Noto Sans Arabic**.
- Use tabular figures for financial values where supported.
- Suggested hierarchy:
  - Screen title: 22–24sp
  - Section title: 16–18sp
  - Body: 14–16sp
  - Metadata: 12–13sp
- Avoid dense text and overly small financial labels.

## 4. Layout and components

- Default page background: `#F5F7FA`.
- Cards: white surface, 12–16dp radius, subtle border; avoid excessive shadows.
- Primary button: navy fill, white label, minimum 48dp height.
- Secondary button: outlined or light surface.
- Inputs: visible labels, clear validation messages, minimum 48dp touch height.
- Lists: clear title, supporting description, status, and trailing amount/action as relevant.
- On phones, prefer stacked list rows over dense tables. Use horizontal scrolling only when necessary.
- Navigation should prioritize the most frequent destinations and avoid crowding the bottom bar.

## 5. Navigation proposal

Proposed primary destinations:

1. الرئيسية
2. الورديات
3. المعدات
4. الحسابات
5. المزيد

The **المزيد** area may contain: السائقون، السلف، المصروفات، المخازن، الخزينة والبنوك، التقارير، الإعدادات.

This is a proposal, not a final information architecture decision. Validate it against real user roles and usage frequency before implementation.

## 6. Financial presentation rules

- Show currency (EGP / جنيه) clearly and consistently.
- Use consistent thousand separators.
- Distinguish income, expense, advance, transfer, and balance by labels and signs, not color alone.
- Show cash and bank balances separately from revenue, expenses, and net result.
- Advances belong to driver/worker balances and must not automatically be presented as operating expenses.
- Estimated operating costs are not actual posted expenses.
- Avoid double-counting when actual expenses have already been recorded.
- Label net result according to the backend accounting definition; do not call it final profit if closing adjustments or other conditions remain.
- Never use fabricated prototype figures as live product data. Prototype sample figures must be explicitly marked as illustrative.

## 7. Required screen states

Every data-driven screen must define:

- Initial/loading state.
- Empty state with a useful next action.
- Loaded state.
- Validation errors.
- Permission/role restriction.
- Network/offline state and retry behavior.
- Server failure state.
- Success feedback after create/update actions.
- Read-only or locked state where business rules prevent editing.

## 8. Accessibility and mobile behavior

- Touch targets should generally be at least 48dp.
- Support Android system text scaling without clipping key actions.
- Keep important actions reachable with one hand where practical.
- Use clear focus, error, and selected states.
- Test RTL, long Arabic labels, small screens, and numeric/currency alignment on a real Android device.

## 9. Implementation boundary

This document is a design reference, not authorization to change application code. Flutter implementation begins only after the relevant screen is approved and its backend behavior is confirmed. Platform Owner Web requires a separate responsive specification.

## 10. Versioning

- `v1.0`: initial visual and UX baseline.
- Each screen has its own review/approval checkpoint.
- Changes to shared tokens require a version note.
- Keep the progress tracker updated whenever a screen changes status.
